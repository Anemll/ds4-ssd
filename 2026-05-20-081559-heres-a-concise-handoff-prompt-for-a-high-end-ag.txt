  ---
  Plan: make GPU+ANE prefill beat GPU-only

  Diagnosis (verified, with line numbers)

  The combined path is slower than GPU-only because launching an ANE job forces 
  the GPU prefill stream to drain, waiting on ANE forces another drain, and
  finishing ANE forces a third drain plus a synchronous CPU→GPU writeback on the
   main thread. The "overlap scheduler" plans which groups go to which engine
  but the runtime then serializes them. ANE work also picks atrocious batch
  sizes for ~65% of calls.

  Bug 1 — Dequant drains the GPU on every ANE submit

  ds4_metal.m:15013 calls ds4_gpu_end_commands() immediately on entry to
  ane_start_tensor(). Lines 15034–15065 then encode mpp_dequant_iq2_xxs_i8 +
  mpp_dequant_q2_k_i8 + mpp_quant_f32_i8 into a fresh command buffer and
  ds4_gpu_end_commands() again at 15065. So every ANE job:
  1. forces the in-flight GPU prefill CB to flush,
  2. encodes dequant on the same queue,
  3. flushes again before the CPU threads spawn.

  g_ane_prefill_dequant_ms = 13.3s — that's 13.3s of GPU time that runs instead 
  of, not alongside, the GPU prefill stream. The scheduler thinks ANE is free;
  it isn't.

  Bug 2 — WAIT_ACTIVE_ANE_PREDICT drains GPU before a CPU pthread_join

  ds4.c:10716–10735. The macro calls ds4_gpu_end_commands() before
  wait_predict_tensor(), which is a pthread_join on the CPU ANE eval thread
  (ds4_metal.m:15183–15193). The CPU join has no GPU dependency, so the flush is
   pure overhead — once per ANE wave.

  Bug 3 — FINISH_ANE_SLOT drains GPU, blocks main thread on CPU→GPU memcpy, then
   reopens

  ds4.c:10682–10715 + ds4_metal.m:15196–15244. Sequence per finished ANE group:
  - ds4_gpu_end_commands() (10686)
  - pthread_join ane + post threads (15205–15211)
  - ds4_gpu_tensor_write(out_f32, ...) — synchronous CPU→GPU copy of the
  per-expert output buffer (15236)
  - ds4_gpu_begin_commands() (10696)
  - ds4_gpu_scatter_add_rows_f32_tensor (10700)

  Main thread is parked through the whole thing. With 18,789 ANE calls, even a
  small per-call stall dominates.

  Bug 4 — output_pack and writeback cannot be overlapped with the next ANE/GPU 
  work

  post_thread only does CPU output_pack (g_ane_prefill_output_ms = 5.8s).
  Writeback is held until finish_tensor is called on the main MoE loop, so it
  runs serially with the rest of the loop instead of being chained at the end of
   post_thread.

  Bug 5 — B64 wave is destroying throughput

  Histogram: B64=12140 calls, util=23.2%. That's 65% of all ANE calls running at
   less than ¼ of theoretical occupancy. The scheduler's ane_min_util=0.75 guard
   at ds4.c:9994 only kicks in when refs >= hybrid_ane_min_refs; for refs in the
   8–63 range, can_chunk is likely false and the whole group still gets pushed
  to ANE as B64. The scheduler also uses ane_call_refs=96 as a fixed per-call
  cost that's wildly low compared to the real ~0.7ms dequant + ANE-launch cost
  each call.

  Bug 6 — Cost model ignores GPU-drain penalty

  build_flash_prefill_overlap_plan (9933–10113) charges ANE work
  padded_refs/ane_rel_speed + ane_call_refs and GPU work refs. There's no term
  for "every ANE group costs the GPU an end+begin and a memcpy." So the
  scheduler picks ANE eagerly even when net throughput drops.

  ---
  Fix order (smallest-blast-radius first)

  I'd land these as separate commits and measure after each.

  Phase 1 — Stop the drains (the biggest win, lowest risk)

  1. Remove end_commands from WAIT_ACTIVE_ANE_PREDICT (ds4.c:10719–10722). The
  predict-wait only joins a CPU thread; nothing it touches lives on the GPU
  queue. Keep commands_open as-is so the GPU prefill loop continues encoding
  while ANE runs.
  2. Remove end_commands from FINISH_ANE_SLOT (ds4.c:10685–10688) and reorder
  the macro:
    - Issue the writeback tensor_write from post_thread (last step in
  ds4_gpu_ane_prefill_post_thread, ds4_metal.m:14880+) into a dedicated
  MTLBuffer that's already attached to the tensor's storage. tensor_write on a
  managed buffer is a memcpy + didModifyRange; safe from another thread as long
  as no GPU CB has it encoded yet.
    - In FINISH_ANE_SLOT, pthread_join post_thread (cheap once writeback already
   finished), then encode scatter_add_rows_f32_tensor into the already-open GPU
  command buffer.
  3. Don't end the GPU CB inside ane_start_tensor (ds4_metal.m:15013, 15065).
  Encode the dequant kernels into the current command buffer (the prefill
  encoder), so dequant queues behind in-flight GPU prefill work and they
  pipeline naturally on the GPU. If dequant must run on its own CB for ordering,
   submit it without ending the prefill CB — open a second CB on the same queue.

  Expected effect: the GPU prefill stream stops getting flushed 18,789 times;
  dequant overlaps with prefill on-GPU; main thread stops blocking on per-call
  CPU→GPU memcpy.

  Phase 2 — Kill the low-util B64 wave

  4. Force B64/B128 to GPU at the scheduler. In build_flash_prefill_overlap_plan
   (9994) extend the "send the tail to GPU" check to also send the whole group
  to GPU when ane_batch <= 128 && group_util < ane_min_util. Equivalent at
  runtime: set DS4_FLASH_MOE_ANE_BATCHES=256,512 and
  DS4_FLASH_MOE_SCHED_ANE_MIN_UTIL=0.85 — we'll try the env knob first to
  validate, then bake it in.
  5. Recalibrate the ANE cost model (9967–9974). Replace ane_call_refs=96 with a
   measured per-call cost from g_ane_prefill_dequant_ms / eval_calls + 
  ane_kernel_launch_overhead_ms_to_refs. Easiest: expose
  DS4_FLASH_MOE_SCHED_ANE_CALL_MS (default ~0.5ms) and convert to refs using the
   observed GPU refs/ms throughput cached on the engine state.

  Phase 3 — Real pipelining

  6. True double-buffer ANE jobs. The existing active_ane_job / ready_ane_job
  pair (10674–10679) suggests this is intended but the synchronous waits in
  Phase 1 collapse it to single-buffer. After Phase 1, verify a second ANE job
  can launch while the first's post_thread is still writing back, by allocating
  two sets of dequant scratch buffers (the g_ane_prefill_*_buffer globals at
  15015–15030 are currently shared across calls, which is a real hazard once we
  stop draining — needs a small ring of N=2 or N=4 scratch sets keyed by job
  slot).
  7. Move output_pack to GPU if Instruments still shows the post_thread on the
  critical path. The scaling-by-route-weight loop at ds4_metal.m:14902–14911 is
  trivially a Metal kernel that reads out_f16_batch and writes directly into the
   destination tensor — eliminates the CPU buffer entirely and folds output_pack
   + writeback into one GPU dispatch encoded on the prefill CB.

  Architecture for the multi-expert CoreML model:

  The constraint that makes "per-row gather" not work directly:
  gather(weights[expert_idx]) produces a tensor of shape (B, H, I) = ~2 GiB at
  B=256 — too big for ANE.

  The viable pattern: model takes a small set of K experts' stacked weights and
  a per-row expert index. Internally it loops K times (compile-time unrolled),
  each iteration doing one expert's full matmul on all B rows, then masks the
  result by the rows that actually use that expert. Compute is K× single-expert,
   but K-call overhead becomes 1-call overhead. Win iff per-call overhead ×
  (K-1) > extra compute time for K-1 experts on irrelevant rows.

  Let me start by implementing the standalone Python export + numerical
  validation.

  What the data confirms about bubbles

  Per-call wall (~2.35 ms) vs ane_eval per-call (~190 µs) means >90% of each 
  per-ANE-call window is non-ANE-compute.

  What the bubbles are made of (with how to test each)

  Bubble source: A. Per-call GPU dequant on shared queue
  Test: Already known — dequant_ms field in stats
  Fixable how?: We already made dequant async in Phase 1 (saved 1.3s on

  Bubble source: B. Per-call CPU output_pack
  Test: output_ms field, ~1.4 ms/chunk

  The floor is 1.12 ms/call — ANE silicon throughput when the framework keeps it
   busy. With 4-way concurrent submission, the framework hides 100% of the 
  weight upload cost behind other ctxs' evaluates. So multi-ctx parallel ANE is 
  the lever, not weight reuse.

  Recommendations ranked by expected gain

  1. ds4 production integration of multi-ctx parallel ANE submission — biggest
  single fix. Convert the current single-ctx pipeline (with shared _ANERequest
  and IOSurfaces) into a ring of N=4 ctx instances, each with private bound
  surfaces. Scheduler dispatches expert work round-robin. Expected production
  impact:
  - ANE-only mode: 88 → ~115 t/s (the bubbles get filled — directly addresses
  user's observation)
  - Combined mode: ~190 → ~193 t/s (modest, because GPU was already filling most
   bubbles)
  - Approximate cost: ~300-500 LOC. The existing ane_ds4_mlp_int8w.m structure
  already supports per-ctx isolation; mostly need to multiply allocations and
  add round-robin in the scheduler.

  2. Skip weight rewrite when consecutive ANE calls hit the same expert — small
  but free. Only valuable if the same expert appears back-to-back in the plan
  (need to check the plan ordering). The new
  ds4_ane_mlp_i8w_i8x_tiled_fused_eval_xonly API I just added makes this trivial
   to wire in.

  3. Skip output read when the result will be immediately overwritten — only 4%
  of wall, not worth a refactor.

  4. CPU output_pack moved to GPU in ANE-only mode — would help ANE-only further
   (currently the post_thread is on the bubble critical path); for combined mode
   the GPU is the bottleneck so this regresses (we already proved that with
  Phase 3).

  Where the residual ~5% combined-vs-GPU-only gap actually comes from

  The data now makes this clear: it's not call overhead, not weight uploads, not
   output reads, not pthread waits. It's that ANE genuinely runs at ~1.12 
  ms/call best-case, and offloading ~5% of refs to ANE for ~1 ms/call costs more
   than the parallel GPU savings. To beat GPU-only, you need either (a) ANE to
  handle MORE refs (per-row routing — proven not viable on ANE), or (b)
  something on the GPU side to actually pay back the ANE overhead (e.g., GPU
  doing a different kind of work in parallel — like attention prefill while MoE
  prefill is on ANE — which is a much bigger architectural change).
